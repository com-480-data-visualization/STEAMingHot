## 1. Type Annotations

In JS you just write `let x = 5`. In TS you can explicitly annotate types:

```typescript
let age: number = 25;
let name: string = "Alice";
let active: boolean = true;

function greet(name: string): string {
    return `Hello, ${name}`;
}
```

TS also has **type inference**: if you write `let x = 5`, TS already knows it's a `number`. You don't always need to annotate explicitly, but you should for function parameters and return types.

## 2. Basic Types

```typescript
let a: string = "hello";
let b: number = 42;          // covers int, float, etc.
let c: boolean = true;
let d: null = null;
let e: undefined = undefined;

let f: any = "anything";     // disables type checking — avoid it
let g: unknown = "something"; // like any, but safer (must narrow before use)
let h: never = ...;          // a value that never occurs (e.g. exhaustive checks, infinite loops)
let i: void = undefined;     // used as return type for functions that return nothing
```

The key distinction: `any` lets you do anything with the value with no checks. `unknown` forces you to check the type before using it. Always prefer `unknown` over `any`.

```typescript
function process(val: unknown) {
    if (typeof val === "string") {
        console.log(val.toUpperCase()); // OK, narrowed to string
    }
}
```

## 3. Arrays & Tuples

```typescript
// Arrays — two equivalent syntaxes
let nums: number[] = [1, 2, 3];
let strs: Array<string> = ["a", "b"];

// Tuples — fixed length, fixed types at each position
let pair: [string, number] = ["Alice", 30];
let first = pair[0]; // type: string
let second = pair[1]; // type: number

// Optional tuple elements
let maybe: [string, number?] = ["Alice"];

// Named tuples (more readable)
let point: [x: number, y: number] = [10, 20];
```

Tuples are useful when you want to return multiple values from a function with precise types (like React's `useState` which returns `[T, Dispatch<T>]`).

## 4. Union & Intersection Types

**Union** (`|`): the value can be one of several types.

```typescript
let id: string | number = 42;
id = "abc"; // also valid

function printId(id: string | number) {
    if (typeof id === "string") {
        console.log(id.toUpperCase());
    } else {
        console.log(id.toFixed(2));
    }
}
```

**Intersection** (`&`): the value must satisfy all types at once. Used to combine object shapes.

```typescript
type A = { name: string };
type B = { age: number };
type AB = A & B;

const person: AB = { name: "Alice", age: 30 }; // must have both
```

## 5. Type Aliases & Interfaces

Both let you name and reuse custom types. They look similar but have differences.

**Type alias** — can describe any type, not just objects:

```typescript
type ID = string | number;
type Point = { x: number; y: number };
type Callback = (err: Error | null, result: string) => void;
```

**Interface** — only for object shapes, but supports declaration merging and is preferred for public APIs:

```typescript
interface User {
    name: string;
    age: number;
}

// Extending interfaces
interface Admin extends User {
    role: string;
}

// Declaration merging (unique to interfaces)
interface Window {
    myCustomProp: string;
}
```

**When to use which:**
Use `interface` for object shapes you might extend or that are part of a public API. Use `type` for everything else (unions, intersections, primitives, function signatures, etc.). In practice, many teams just pick one and stick with it.

## 6. Optional & Default Properties

```typescript
// Optional property on an object
interface Config {
    host: string;
    port?: number; // can be number or undefined
}

// Optional parameter in a function
function connect(host: string, port?: number) {
    console.log(host, port ?? 3000);
}

// Default parameter (plain JS, still works in TS)
function connect2(host: string, port: number = 3000) {
    console.log(host, port);
}
```

The difference: `port?: number` means the caller can omit it (it'll be `undefined`). `port: number = 3000` means it defaults to 3000 if omitted.

## 7. Type Assertions & Non-null Assertion

Sometimes you know more about a type than TS does. You can override its inference.

**Type assertion** with `as`:

```typescript
const input = document.getElementById("myInput") as HTMLInputElement;
console.log(input.value); // TS now knows it's an input element

// Alternative angle-bracket syntax (not usable in JSX)
const input2 = <HTMLInputElement>document.getElementById("myInput");
```

**Non-null assertion** with `!`: tells TS "trust me, this is not null or undefined":

```typescript
const el = document.getElementById("app")!; // removes null from the type
el.innerHTML = "Hello"; // no error
```

Use these sparingly. They bypass the type checker, so if you're wrong, you get runtime errors.

## 8. Enums

Enums let you define a set of named constants.

**Numeric enum** (default):

```typescript
enum Direction {
    Up,    // 0
    Down,  // 1
    Left,  // 2
    Right  // 3
}

let dir: Direction = Direction.Up;
```

**String enum** (more explicit, better for debugging):

```typescript
enum Status {
    Active = "ACTIVE",
    Inactive = "INACTIVE",
    Pending = "PENDING"
}
```

**`const enum`**: inlined at compile time, produces no JS object at runtime (more performant):

```typescript
const enum Color {
    Red,
    Green,
    Blue
}

let c = Color.Red; // compiled to just: let c = 0;
```

A common alternative to enums is using a union of string literals, which many TS developers prefer:

```typescript
type Direction = "Up" | "Down" | "Left" | "Right";
```

This is simpler and avoids some quirks of enums (like reverse mapping in numeric enums).

## 9. Generics

Generics let you write code that works with any type while still being type-safe. This is one of the most important features in TS.

```typescript
// Without generics, you'd use any (bad)
function identity(val: any): any { return val; }

// With generics
function identity<T>(val: T): T { return val; }

let x = identity<string>("hello"); // x is string
let y = identity(42);              // TS infers T = number
```

**Generic interfaces and types:**

```typescript
interface Box<T> {
    value: T;
    label: string;
}

let box: Box<number> = { value: 42, label: "age" };
```

**Generic constraints** — restrict what `T` can be:

```typescript
function getLength<T extends { length: number }>(val: T): number {
    return val.length;
}

getLength("hello"); // OK
getLength([1, 2, 3]); // OK
getLength(42); // Error: number has no .length
```

**Multiple type parameters:**

```typescript
function pair<K, V>(key: K, val: V): [K, V] {
    return [key, val];
}
```

You'll see generics everywhere: `Array<T>`, `Promise<T>`, `Map<K, V>`, etc.

## 10. Narrowing & Type Guards

Narrowing is how TS refines a broad type into a more specific one inside a block.

**`typeof` narrowing:**

```typescript
function process(val: string | number) {
    if (typeof val === "string") {
        // val is string here
        console.log(val.toUpperCase());
    } else {
        // val is number here
        console.log(val.toFixed(2));
    }
}
```

**`instanceof` narrowing:**

```typescript
function handle(err: Error | string) {
    if (err instanceof Error) {
        console.log(err.message);
    }
}
```

**`in` narrowing** (checks if a property exists on an object):

```typescript
type Cat = { meow: () => void };
type Dog = { bark: () => void };

function speak(animal: Cat | Dog) {
    if ("meow" in animal) {
        animal.meow(); // animal is Cat here
    } else {
        animal.bark();
    }
}
```

**Custom type guards** with `is`:

```typescript
function isString(val: unknown): val is string {
    return typeof val === "string";
}

if (isString(someValue)) {
    console.log(someValue.toUpperCase()); // narrowed to string
}
```

The return type `val is string` is a **type predicate**. It tells TS: "if this function returns true, narrow the argument to `string`."

## 11. Utility Types

TS ships with built-in generic types that transform existing types. These save you a ton of boilerplate.

```typescript
interface User {
    id: number;
    name: string;
    email: string;
    age: number;
}

// Partial — makes all properties optional
type PartialUser = Partial<User>;
// { id?: number; name?: string; email?: string; age?: number }

// Required — makes all properties required
type RequiredUser = Required<PartialUser>;

// Readonly — prevents reassignment
type ReadonlyUser = Readonly<User>;
// readonlyUser.id = 1; // Error

// Pick — keep only listed properties
type UserPreview = Pick<User, "id" | "name">;
// { id: number; name: string }

// Omit — remove listed properties
type UserWithoutEmail = Omit<User, "email">;

// Record — build an object type from keys and value type
type Roles = Record<"admin" | "user" | "guest", boolean>;
// { admin: boolean; user: boolean; guest: boolean }

// ReturnType — extract return type of a function
function fetchUser() { return { id: 1, name: "Alice" }; }
type FetchResult = ReturnType<typeof fetchUser>;
// { id: number; name: string }

// Parameters — extract parameter types as a tuple
type Params = Parameters<typeof fetchUser>;

// NonNullable — removes null and undefined
type MaybeString = string | null | undefined;
type DefinitelyString = NonNullable<MaybeString>; // string
```

## 12. Literal Types & Template Literal Types

**Literal types**: instead of `string`, you constrain to a specific string (or number/boolean) value.

```typescript
type Direction = "left" | "right" | "up" | "down";
type StatusCode = 200 | 404 | 500;
type Bool = true; // only the value true

function move(dir: Direction) { ... }
move("left");  // OK
move("sideways"); // Error
```

**Template literal types**: apply string template logic at the type level.

```typescript
type EventName = "click" | "focus" | "blur";
type Handler = `on${Capitalize<EventName>}`;
// "onClick" | "onFocus" | "onBlur"

type CSSProperty = `${string}-${"top" | "bottom" | "left" | "right"}`;
// "padding-top" | "padding-bottom" | "margin-left" | etc.
```

These are powerful for typing things like event handler names, CSS properties, or API route patterns.

## 13. `keyof` & `typeof` Operators

**`keyof`**: produces a union of the keys of a type.

```typescript
interface User { id: number; name: string; email: string; }

type UserKeys = keyof User; // "id" | "name" | "email"

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}

const user: User = { id: 1, name: "Alice", email: "a@b.com" };
const name = getProperty(user, "name"); // type: string
const id = getProperty(user, "id");     // type: number
```

**`typeof`** (in type position): derives a type from a runtime value.

```typescript
const config = { host: "localhost", port: 3000 };
type Config = typeof config; // { host: string; port: number }

// Very useful with const objects used as schemas
const ROLES = { admin: 1, user: 2, guest: 3 } as const;
type Role = keyof typeof ROLES; // "admin" | "user" | "guest"
```

The `as const` assertion is important: it makes TS infer the narrowest possible type (literal types instead of `string`/`number`).

## 14. Mapped Types

Mapped types let you create new types by transforming each property of an existing type. This is how utility types like `Partial` and `Readonly` are actually implemented internally.

```typescript
// Make all properties optional (how Partial<T> works)
type MyPartial<T> = {
    [K in keyof T]?: T[K];
};

// Make all properties readonly
type MyReadonly<T> = {
    readonly [K in keyof T]: T[K];
};

// Make all properties nullable
type Nullable<T> = {
    [K in keyof T]: T[K] | null;
};
```

You can also **remap keys** with `as`:

```typescript
type Getters<T> = {
    [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type UserGetters = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }
```

And you can **filter out keys** by mapping to `never`:

```typescript
type OnlyStrings<T> = {
    [K in keyof T as T[K] extends string ? K : never]: T[K];
};

type Result = OnlyStrings<{ name: string; age: number; email: string }>;
// { name: string; email: string }
```

## 15. Conditional Types

Conditional types let you express type-level logic with an `extends`-based ternary.

```typescript
type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<string>;  // "yes"
type B = IsString<number>;  // "no"
```

**`infer`** — extract a type from within a condition:

```typescript
// Extract the return type of a function (how ReturnType<T> works)
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type R = MyReturnType<() => number>; // number

// Extract element type of an array
type ElementType<T> = T extends (infer E)[] ? E : never;
type E = ElementType<string[]>; // string
```

**Distributive conditional types**: when `T` is a union, the condition is applied to each member:

```typescript
type ToArray<T> = T extends any ? T[] : never;
type Result = ToArray<string | number>; // string[] | number[]
```

## 16. Declaration Files & tsconfig Basics

**Declaration files (`.d.ts`)**: these describe the types of existing JS code without any runtime content. You never import them directly; TS picks them up automatically.

```typescript
// my-lib.d.ts
declare function greet(name: string): string;
declare const VERSION: string;
declare module "my-lib" {
    export function doSomething(): void;
}
```

When you install a package like `lodash`, its types come from `@types/lodash` (from the DefinitelyTyped project). Modern packages often ship their own `.d.ts` files directly.

**`tsconfig.json`** key options:

```json
{
  "compilerOptions": {
    "target": "ES2020",         // what JS version to compile to
    "lib": ["ES2020", "DOM"],   // which built-in type definitions to include
    "strict": true,             // enables all strict checks — always turn this on
    "noImplicitAny": true,      // error on implicit any (included in strict)
    "strictNullChecks": true,   // null/undefined are not assignable to other types (included in strict)
    "moduleResolution": "node", // how to resolve imports
    "outDir": "./dist",         // where compiled JS goes
    "rootDir": "./src",         // where your TS source is
    "esModuleInterop": true     // smoother interop with CommonJS modules
  }
}
```

The single most impactful setting is `"strict": true`. Always enable it. It turns on a suite of checks (`noImplicitAny`, `strictNullChecks`, etc.) that catch most real-world bugs.
